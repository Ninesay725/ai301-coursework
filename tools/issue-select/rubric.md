# Rubric: is this a good first issue?

## Evidence conventions

In eval mode, use only the issue bundle and measure all ages from its captured date. In live mode, use the current date and the sources below, following `references/evidence-guide.md`. Read the issue body and the entire available comment thread before deciding. Later maintainer clarification supersedes earlier uncertainty. State the deciding fact for every check; do not treat a label, popularity, or an attractive title as proof.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Human maintenance | Repo facts: last 5 default-branch commits, maintainer first-response sample, and dated OWNER/MEMBER/COLLABORATOR activity in the issue. Live: default-branch commit history, the authors of merged PRs, this thread, and 5 recently updated issues. | At least one human-authored default-branch commit or bot merge of a human-authored PR within 90 days, OR a maintainer opened or commented on this issue within 90 days, OR at least one sampled issue received a maintainer first response within 30 days of opening and that response occurred within 90 days of the reference date. Automated dependency/generated-file commits alone do not qualify. | required |
| Repository continuity | Repo facts: archived flag, last push to any branch, latest release. Live: repository archive banner/API metadata, branch commit dates, and Releases. | The repository is not archived AND (has a push within 180 days OR a release within 365 days). A repository with no releases can pass on recent pushes; there is no minimum star count. | required |
| Bounded contribution | Issue body, labels, and full comment thread, especially maintainer clarification of the requested change. | The issue asks for one identifiable code, test, documentation, or configuration change. Reject an umbrella/tracking issue with independent subprojects, a pure usage/support question, unresolved competing designs, or an explicit maintainer warning that the fix requires substantial core-internals work. A short description, missing reproduction steps, or a missing good-first-issue label does not by itself fail this check. A checklist implementing one outcome is not an umbrella issue. | required |
| Attempt history | Issue open date, linked PR states, and comments describing abandoned or failed implementations. Live: issue timeline and the referenced PRs. | It is not BOTH older than 730 days AND associated with at least 2 closed-unmerged or explicitly abandoned implementation attempts without a later maintainer-provided bounded resolution. Age alone is not a failure; do not count a merged PR as an abandoned attempt. | required |
| Available work | Issue state, assignees, Development/linked PRs, and claim or PR-reference comments, including later releases of claims. Live: issue sidebar, timeline, comments, and referenced PR state. | The issue is open and unresolved, with no assignee, no open implementation PR (including one referenced only in comments), and no unreleased claim within the last 90 days. A later explicit withdrawal or maintainer invitation to a new contributor clears an old claim. An older claim without an assignee or open PR is not a permanent reservation. If a comment says a PR was opened and its state cannot be verified, mark unclear rather than assume no PR. Apply any explicit live-mode scope house rule to the claim signals it covers. | required |
| Compatible contribution policy | Repo facts: contribution policy. Live: CONTRIBUTING.md in root, .github/ or docs/, linked contributor guidance, AI policy files, and PR-template disclosure requirements. | There is no outright prohibition on the intended AI-assisted contribution workflow. Silence passes after the available policy sources are checked. Disclosure, personal understanding, tests, and human review are conditions to follow, not bans. A ban on fully AI-generated submissions that expressly permits responsible assistive AI use passes; an outright ban that offers no such allowed workflow fails. | required |
| Verification foothold | Issue body and maintainer comments: reproduction input, expected/actual output, named failing test, or concrete acceptance criteria. | At least one concrete input/output example, reproducible command, named relevant test, or observable acceptance criterion is supplied. | preferred |
| Newcomer invitation | Issue labels and maintainer comments. | The issue has a good-first-issue or help-wanted label, or a maintainer explicitly invites a newcomer to implement it. | preferred |

## Verdict rule

Grade each check `pass`, `fail`, or `unclear`. Return `accept` only when **every required check is pass**; any required `fail` or `unclear` returns `reject`. `unclear` means the necessary evidence remains absent after checking its named source, not that the check was skipped. An explicit `none`, no releases, or a policy statement saying no restriction is evidence, not missing data. For negative-risk checks, do not invent a blocker when the complete available evidence contains none.

Preferred checks never change accept/reject. Use them and the actual fit profile only to rank already accepted issues. Personal familiarity cannot rescue a rejected issue or reject an accepted one. In eval mode, ignore the live scope and fit profile entirely.
